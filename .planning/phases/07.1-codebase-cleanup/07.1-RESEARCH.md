# Phase 7.1: Codebase Cleanup - Research

**Researched:** 2026-02-05
**Domain:** Python code refactoring, technical debt reduction
**Confidence:** HIGH

## Summary

Phase 7.1 addresses accumulated technical debt in a Python trading bot codebase with 10 strategy implementations. The primary issues are code duplication (10 identical `_to_side()` functions, duplicate enum definitions), large unfocused modules (replay.py at 821 lines), dead code (optimizer_old.py at 877 lines), and missing test coverage for 4 strategies.

The codebase analysis reveals:
- **Duplication hotspots**: Every strategy file contains identical `_to_side()` helper, `_check_hourly_reset()` pattern duplicated across strategies, and OrderType enum defined in both `src/strategies/base.py` and `src/core/types.py`
- **Test coverage gaps**: price_level, velocity, momentum, and spread_aware strategies lack dedicated unit tests (only covered by parameterized tests in test_strategies.py)
- **Module size**: replay.py (821 lines) mixes responsibilities: session loading, event processing, result calculation, analysis tracking
- **PnL calculation**: Each strategy implements `calculate_pnl()` independently (10 implementations)

**Primary recommendation:** Use extract-method refactoring to consolidate utilities, mixin pattern for shared strategy behaviors, pytest parameterization for strategy testing, and module splitting for replay.py into focused components (<300 lines each).

### Pattern 1: Extract Common Utilities
**What:** Create `src/strategies/utils.py` to hold duplicated helper functions
**When to use:** When 3+ implementations share identical code
**Example:**
```python

"""Shared utility functions for all strategies."""
from ...core.types import Side
from ...data.models import TradeSide

    """Convert TradeSide to Side enum.

    Centralized conversion used by all strategies.
    """
    return Side.UP if side == TradeSide.UP else Side.DOWN
```

### Pattern 2: Mixin Classes for Common Strategy Behavior
**What:** Extract shared methods into mixin classes that strategies inherit
**When to use:** When multiple strategies share behavioral patterns (not just utilities)
**Example:**
```python
# src/strategies/mixins.py
"""Mixins for common strategy behaviors."""
from decimal import Decimal
from datetime import datetime
from typing import Optional
from .base import TradeDecision, DecisionAction

class HourlyBudgetMixin:
    """Provides hourly budget tracking and reset logic."""

    def __init__(self):
        self.hourly_budget_used = Decimal("0")
        self._current_hour: Optional[int] = None

    def check_hourly_reset(self, event_time: datetime) -> None:
        """Reset hourly budget if hour changed."""
        current_hour = event_time.hour
        if self._current_hour is not None and current_hour != self._current_hour:
            self.hourly_budget_used = Decimal("0")
        self._current_hour = current_hour

class ExtremeCheckMixin:
    """Provides extreme price checking logic."""

    def check_extreme_prices(self, price: Decimal, action: str) -> Optional[str]:
        """Check if price is in extreme range that should skip.

        Returns skip_reason if should skip, None otherwise.
        """
        from .base import PRICE_EXTREME_HIGH, PRICE_EXTREME_LOW

        if price >= Decimal("1.0"):
            return "invalid_price"
        if price <= PRICE_EXTREME_LOW:
            return "price_extreme_low"
        if action == "BUY" and price >= PRICE_EXTREME_HIGH:
            return "price_extreme_high"
        return None

class SkipHelperMixin:
    """Provides skip() helper for creating skip decisions."""

    def skip(self, reason: str) -> TradeDecision:
        """Create a SKIP decision with reason."""
        self.skips += 1
        self.skip_reasons[reason] = self.skip_reasons.get(reason, 0) + 1
        return TradeDecision.skip(reason)

# Usage in strategy:
class ProfitTakerStrategy(HourlyBudgetMixin, ExtremeCheckMixin, SkipHelperMixin, Strategy):
    """Strategy using mixins."""

    def __init__(self):
        HourlyBudgetMixin.__init__(self)
        # ... rest of init

    def on_event(self, event: MarketEvent) -> TradeDecision:
        self.check_hourly_reset(event.trade.timestamp)

        skip_reason = self.check_extreme_prices(prices.ask, "BUY")
        if skip_reason:
            return self.skip(skip_reason)
        # ... rest of logic
```

**Mixin ordering:** Mixins must come BEFORE the base class in inheritance order due to Python's Method Resolution Order (MRO).

### Anti-Patterns to Avoid
- **Over-abstracting**: Don't extract a function used by only 1-2 strategies. Wait for 3+ uses.
- **Deep inheritance hierarchies**: Keep mixin depth to 2-3 levels maximum. Deep hierarchies are hard to debug.
- **Breaking backward compatibility**: Use `__init__.py` re-exports when splitting modules to maintain import paths.
- **Incomplete refactoring**: If extracting a function, extract ALL instances. Partial extraction creates inconsistency.
- **Testing after refactoring**: Always run tests BEFORE starting refactoring to ensure clean baseline.

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Finding duplicate code | Manual grep/search | rope or PyCharm refactoring | AST-based detection catches semantic duplicates, not just textual |
| Dead code detection | Manual review | vulture or deadcode | AST analysis finds truly unused code including dynamic imports |
| Test isolation after refactoring | Manual verification | pytest with coverage | Coverage report shows exactly what's tested and what breaks |
| Enum consolidation | Copy-paste | Type checking with mypy | Mypy catches enum mismatches at static analysis time |
| Module splitting | Manual file creation | rope.refactor.restructure | Rope handles import updates automatically |

**Key insight:** Refactoring tools use Abstract Syntax Tree (AST) analysis to understand code semantically, not just textually. Manual refactoring often misses edge cases (dynamic imports, string references, metaclass magic) that AST-based tools catch.

## Common Pitfalls

### Pitfall 1: Breaking Existing Tests During Refactoring
**What goes wrong:** Tests start failing after refactoring even though "nothing should change"
**Why it happens:**
- Imports break when moving code between modules
- Test fixtures reference old module paths
- Private methods (_prefixed) get renamed but tests still use old names
**How to avoid:**
1. Run full test suite BEFORE starting (establish green baseline)
2. Use `pytest-cov` to track coverage before/after
3. Keep test file structure parallel to source structure
4. Use `__init__.py` re-exports to maintain backward compatibility
**Warning signs:**
- ImportError exceptions in tests
- Tests that passed before refactoring now fail
- Coverage drops after refactoring

### Pitfall 2: Incomplete Duplication Removal
**What goes wrong:** Extract a common function but miss 1-2 instances, leaving partial duplication
**Why it happens:**
- Search doesn't catch slight variations (`_to_side` vs `to_side` vs `convert_side`)
- Forgot to check test files
- Dynamic/conditional code paths not obvious
**How to avoid:**
1. Use AST-based search (rope, not grep) to find semantic duplicates
2. After extraction, search for the old pattern again - should find zero results
3. Add a comment in the original location pointing to new location
4. Use mypy to catch type mismatches if you missed instances
**Warning signs:**
- Finding "one more instance" during code review
- Tests for new utility function don't cover all edge cases
- Different strategies still have slightly different implementations

### Pitfall 3: Mixin Method Resolution Order (MRO) Confusion
**What goes wrong:** Mixin methods don't get called, or wrong version gets called
**Why it happens:** Python's MRO processes base classes right-to-left, but mixins must come left-most
**How to avoid:**
1. Always put mixins BEFORE the main base class: `class MyStrategy(Mixin1, Mixin2, Strategy)`
2. Use `super().__init__()` calls in mixins to chain initialization
3. Test MRO with `ClassName.__mro__` to verify order
4. Each mixin should have single responsibility (one behavioral aspect)
**Warning signs:**
- Mixin methods never execute
- `AttributeError` for methods that should exist
- Initialization not running
- Use `print(MyStrategy.__mro__)` to debug

### Pitfall 4: Losing Dead Code Context
**What goes wrong:** Delete "unused" code that's actually referenced dynamically or in comments/docs
**Why it happens:**
- Dynamic imports: `__import__(module_name)`
- String-based lookup: `getattr(obj, method_name)`
- Comments reference code but AST doesn't see it
- Code used only in production, not tests
**How to avoid:**
1. Use `deadcode` instead of `vulture` (more accurate)
2. Check git history before deleting - when was it last modified?
3. Search codebase for string references to filename/function
4. If uncertain, move to `deprecated/` folder for one release cycle
5. Document WHY code was removed in commit message
**Warning signs:**
- "This should never happen" comments near unused code
- Large functions (>100 lines) flagged as unused
- Code in `__main__` blocks flagged as unused

### Pitfall 5: Splitting Modules Without Clear Boundaries
**What goes wrong:** Split a large module but boundaries are unclear, leading to circular imports
**Why it happens:**
- Split by line count not by responsibility
- Didn't identify data flow and dependencies first
- Classes/functions too tightly coupled
**How to avoid:**
1. Draw dependency graph BEFORE splitting (what calls what?)
2. Split by responsibility: loading, processing, results
3. Use dataclasses/models for data passed between modules
4. Avoid circular imports: if A imports B and B imports A, merge or extract interface
5. Test imports independently: `python -c "from module import X"`
**Warning signs:**
- `ImportError: cannot import name 'X' from partially initialized module`
- Modules with many cross-imports
- Difficulty naming modules (usually means unclear boundaries)

### Pitfall 6: Over-Reliance on Test Suite During Refactoring
**What goes wrong:** Tests pass but production behavior changes subtly
**Why it happens:**
- Tests don't cover edge cases
- Integration tests missing
- Tests mock too much (passing but not realistic)
**How to avoid:**
1. Check test coverage with `pytest --cov` before refactoring - aim for >80%
2. Add integration tests for critical paths
3. Manual smoke test after refactoring: run actual replay
4. Compare outputs before/after: save results, diff them
**Warning signs:**
- Very high unit test coverage but low integration coverage
- Tests using lots of mocks
- "Works in tests but not production"
